## What is not satisfied yet (8)

### transcript

- Status: n/a
- Needs: transcript, pty
- Why: core does not advertise the "transcript" capability
- Asserts: subscribing is answered at once with the history the core kept as one replay frame, every record read afterwards arrives as a live batch whose seq numbers are strictly above the replayed ones, so a client that appends by seq and drops a seq it already holds loses nothing and duplicates nothing, and no batch is pushed after unsubscribe.

### queue-edit

- Status: n/a
- Needs: queue, queueEdit, pty
- Why: core does not advertise the "queueEdit" capability
- Asserts: a pending message's text can be rewritten by the id its snapshot gave it, and the occurrence keeps that id and its position in delivery order rather than being cancelled and requeued behind everything after it; an id that names no pending occurrence is refused with queue-item-not-found and changes nothing.

### transcript-activity

- Status: n/a
- Needs: transcript, pty
- Why: core does not advertise the "transcript" capability
- Asserts: a session whose CLI is appending records to its own stream-json transcript reads busy even though nothing painted a working footer, and the records a transcript already held when the core first read it do not pulse a session busy at all.

### reaper

- Status: n/a
- Needs: reaper, sessionMeta, pty
- Why: core does not advertise the "reaper" capability
- Asserts: a core that advertises `reaper` honours the two frames a client steers it with. A session left alone for the idle window is flagged dormant on the wire (a sessionMeta carrying dormant: true) and only then killed, so the row a client keeps says "slept, wake me on demand" rather than "died"; a session the client has declared protected survives the same window untouched, because sleeping the pane somebody is looking at is visible work vanishing under them; and reactivate brings it back with the flag cleared, which is the one click that has to make the moon go away. The live-session ceiling travels on the same frame and is driven here, but which session it evicts is asserted in the core's own suite, where the session set is controlled - a conformance run shares one daemon with every scenario before it, so an LRU order over that daemon's whole session list is not a fact this file can pin.

### stuck

- Status: n/a
- Needs: stuck, pty
- Why: core does not advertise the "stuck" capability
- Asserts: a session whose CLI writes the same tool call with identical arguments three times in a row is advised about, unsolicited and without anyone subscribing, and the advisory is exactly that - the session keeps running, keeps its pty and answers input afterwards, because the core notifies and never enforces.

### session-list

- Status: n/a
- Needs: sessionList, pty
- Why: core does not advertise the "sessionList" capability
- Asserts: a core that advertises `sessionList` answers `listSessions` with every session it has, to a connection that was not there when they were made. That is the half no delta stream can supply: `created`, `sessionMeta` and `exit` only reach a client that was already connected, so a client fed by those alone starts empty and fills in only as sessions are touched - which under the Rust core meant a sidebar holding 28 sessions against the daemon's 379, and read as having lost every project (juancode-75c5). The frame is a snapshot and not a subscription, so it lists the session created before the connection opened, it lists exited sessions too because history is the thing being restored, and it is answered exactly once per ask.

### session-delete

- Status: n/a
- Needs: sessionDelete, sessionList, isolateWorktree, pty, git
- Why: core does not advertise the "sessionDelete" capability
- Asserts: a core that advertises `sessionDelete` makes a session stop existing, which `kill` never did: the row is gone from the store, so a later attach is an error and a `listSessions` no longer names it, and the worktree an isolated create made is reaped and reported. A killed session is still history to attach to and replay - that is the difference this scenario pins, and the reason the reap is on the delete path and not on the exit edge, since the work in a worktree routinely outlives the agent that did it. Without the frame a rust-mode delete dropped the client's own row while the daemon kept its own, so the session came back on the next list or adopt and its `<repo>-worktrees/<8hex>` tree was left for a sweep to find (juancode-lxe3, juancode-oe30).

### session-sleep

- Status: n/a
- Needs: sessionSleep, sessionMeta, sessionList, pty
- Why: core does not advertise the "sessionSleep" capability
- Asserts: a core that advertises `sessionSleep` lets a client put a session to sleep on purpose, and leaves behind a row that is distinguishable from a kill. The flag lands on the wire BEFORE the pty dies - a `sessionMeta` carrying `dormant: true`, then the `exit` - so the exited row the death finalises reads "slept, wake me on demand" rather than "died"; the core's OWN snapshot says the same thing, which is the half a client cannot supply for itself and the whole reason the frame exists (the desktop's global pause used to send a plain `kill` and write `dormant` onto its private mirror row, so the core, its reaper and its boot-time rehydrate all saw five paused agents as five ended ones - juancode-nizo); a `reactivate` wakes exactly the session it names and clears only that flag, leaving the rest of the paused set asleep, which is what makes "play brings back what pause took" a promise rather than a hope; and a session whose pty is already gone is refused with an `error` instead of flagged, because a crash relabelled as asleep is a row a global play would wake as if somebody had paused it.
